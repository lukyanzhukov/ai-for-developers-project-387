# Календарь звонков

[![hexlet-check](https://github.com/lukyanzhukov/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/lukyanzhukov/ai-for-developers-project-387/actions)

Сервис записи на встречи с одним владельцем календаря. Учебный проект [Хекслета](https://ru.hexlet.io/programs/ai-for-developers) по мотивам [Cal.com](https://cal.com/).
[Исходное задание](https://files.hexlet.app/a/2ipc5m).

## Сценарий записи на звонок

1. Владелец создаёт тип встречи в `/admin`: название, описание и длительность от 1 до 1440 минут. ID можно задать вручную или оставить автоматическим.
2. Гость открывает `/booking`, выбирает тип встречи, дату и свободное время, вводит имя и email. Заметка необязательна.
3. После подтверждения гость видит детали записи. Занятое время становится недоступно для всех типов встреч.
4. Владелец просматривает текущие и будущие встречи в `/admin?view=bookings`. По умолчанию открыт полный список всех типов встреч с группировкой по датам, включая даты за пределами окна записи в 14 дней. Переключатель «Список / Календарь» открывает просмотр выбранного дня; выбранная дата сохраняется при переключении режимов, дополнительных запросов при этом нет. Данные обновляются при открытии и кнопкой «Обновить»; обновление сохраняет режим просмотра. Перезагрузка страницы возвращает режим «Список». При ошибке обновления ранее загруженные встречи остаются с предупреждением о возможной неактуальности. Завершённые встречи исчезают после успешного обновления; автоматического обновления по таймеру нет.

## Правила и ограничения

- Окно записи — сегодня и следующие 13 календарных дней в `Asia/Novokuznetsk`. Рабочее время: Пн–Пт, 09:00–18:00, начало слотов каждые 15 минут. Праздники и перерывы не учитываются.
- Встреча целиком помещается в рабочее время и начинается строго позже текущего времени сервера. Пересечения запрещены; следующая встреча может начаться сразу после предыдущей.
- Сервер повторно проверяет доступность при подтверждении. Из двух конфликтующих запросов успешен один. Повтор с тем же ключом и данными возвращает сохранённую запись.
- **Данные хранятся в памяти одного процесса и теряются при перезапуске или деплое.** Запускайте один экземпляр сервера.
- **Авторизации нет: админка и контактные данные гостей доступны всем.** Используйте вымышленные персональные данные.
- Нет редактирования и удаления типов, отмены и переноса встреч, email-уведомлений, интеграций с календарями и видеозвонками.

## Локальный запуск

Установите [mise](https://mise.jdx.dev/getting-started.html), затем:

```bash
git clone https://github.com/lukyanzhukov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run dev
```

`mise install` устанавливает инструменты и через хук `postinstall` запускает `mise run install`: зависимости по lockfile, Chromium для тестов и Git-хуки hk. После обновления зависимостей повторите `mise run install`. На Linux установка системных библиотек Chromium может потребовать sudo.

Интерфейс: <http://127.0.0.1:5173>, API: <http://127.0.0.1:3000>. Vite проксирует `/api` на сервер.

```bash
mise run status   # состояние фоновых серверов
mise run logs     # логи
mise run stop     # остановка
```

`HOST`, `PORT` и `WEB_PORT` заданы в `mise.toml`. Локальные переопределения храните в игнорируемом `mise.local.toml`; при смене портов обновляйте `ready_port` процессов.

Собранное приложение отдаёт интерфейс и API с одного адреса:

```bash
mise run build
mise run start    # http://127.0.0.1:3000, остановка Ctrl+C
```

## Разработка

TypeScript, Node.js, Fastify; React, Vite и Mantine. Версии инструментов — в `mise.toml`, зависимости — в `package.json` и `pnpm-lock.yaml`.

- `server/` — сервер и хранение данных в памяти.
- `web/` — интерфейс.
- `api/main.tsp` — контракт TypeSpec.
- `generated/` — OpenAPI, Fetch SDK, серверные типы и JSON Schema.
- `tests/` — тесты Vitest, HTTP-проверки через SDK и браузерные сценарии Playwright.
- `scripts/` — генерация и проверки коммитов и деплоя.
- `GLOSSARY.md`, `docs/adr/` — термины и решения; `AGENTS.md` — инструкции для агентов.

Цикл разработки и артефакты описаны в [правилах трекера](docs/agents/issue-tracker.md#workflow-and-artifacts). При разборе идеи агент предлагает, стоит ли проверить её на макетах до спецификации. Этот этап включается только по вашему явному согласию: макеты проходят итерации ревью и приёмку, затем согласованный дизайн учитывается в спецификации и GitHub-задачах.

### API

| Метод | Путь                                   | Назначение                               |
| ----- | -------------------------------------- | ---------------------------------------- |
| GET   | `/api/health`                          | Проверка готовности: `{"status":"ok"}`   |
| GET   | `/api/meeting-types`                   | Список типов встреч                      |
| POST  | `/api/meeting-types`                   | Создание типа встречи                    |
| GET   | `/api/meeting-types/{id}/availability` | Свободные слоты                          |
| POST  | `/api/bookings`                        | Подтверждение записи с `Idempotency-Key` |
| GET   | `/api/bookings`                        | Будущие и текущие встречи всех типов     |

Поля, ограничения и ответы описаны в [api/main.tsp](api/main.tsp). Даты календаря относятся к часовому поясу владельца, моменты начала и окончания передаются в UTC.

После изменения контракта выполните `mise run generate` и закоммитьте `generated/`. Эти файлы не редактируют вручную. `mise run check` повторяет генерацию и выявляет расхождения, оставляя обновлённые файлы для проверки.

Маршруты Fastify зарегистрированы вручную: генератор Hey API выпускает типы обработчиков и схемы, но не регистрацию маршрутов.

### Проверки и коммиты

```bash
mise run check          # генерация, линтер, форматирование, workflow, типы, тесты и коммиты
mise run test           # сборка и Vitest, включая Chromium
mise run lint
mise run format:check
mise run typecheck
mise run fix            # автоисправления и форматирование
```

hk проверяет изменённые файлы перед коммитом, commitlint — сообщение коммита, полный `check` выполняется перед push и в CI. Формат сообщений — Conventional Commits, например `feat: запись на свободный слот (#12)`.
Учебный `.github/workflows/hexlet-check.yml` и имя репозитория сохраняйте без изменений.

### Команды ИИ-агенту в GitHub

Используется установленный на репозиторий **OpenCode GitHub App** (`opencode-agent[bot]`). Workflow [opencode.yml](.github/workflows/opencode.yml) обрабатывает `issue_comment` и `pull_request_review_comment`, в обоих случаях только `types: [created]`. Он запускает анализ или изменение по команде владельца репозитория и публикует ответ в issue или PR со ссылкой на прогон Actions. Если запрос требует изменений кода, интеграция OpenCode может подготовить ветку и PR; правила согласования из `AGENTS.md` продолжают действовать.

Набор `mentions` задан явно через `MENTIONS: /oc,/opencode`: `/oc <задача>` и `/opencode <задача>` — два равнозначных способа вызвать агента. Команда должна быть отдельным словом; например, `/octopus` не является вызовом. Для проверки добавьте в issue комментарий:

```text
/oc explain this issue
```

Ожидаемый результат — ответ `opencode-agent[bot]` в той же issue и успешный запуск **OpenCode** с событием `issue_comment` в Actions. Сам факт появления строки запуска или ответа отдельного triage не подтверждает выполнение команды. При сбое ответ может отсутствовать; причину смотрите в шагах запуска.

Доверенным участником для команд считается только владелец репозитория (`github.repository_owner`) с типом аккаунта `User`. Команды ботов, других пользователей и изменения старых комментариев не запускают агента. Для PR проверяется через GitHub API, что `head.repo.full_name` и `base.repo.full_name` совпадают с текущим репозиторием. Проверка выполняется также для обычного комментария к PR, где payload события не содержит `head`. Fork PR, удалённый исходный репозиторий и ошибка проверки не допускаются к шагам установки и передачи ключа модели. Для комментариев к строкам fork PR дополнительно исключается весь job ещё до checkout. Проверка допуска покрыта `mise run agents:test` и входит в `mise run check`.

Для авторизации используется стандартная схема OpenCode App: `contents: read` для checkout и `id-token: write` для обмена OIDC на токен установленного App. Дополнительное `pull-requests: read` нужно для проверки происхождения PR. У checkout задано `persist-credentials: false`. Ключ модели хранится в Actions secret `OPENCODE_API_KEY` и передаётся только шагу агента после успешной проверки допуска.

Вместо установочного `anomalyco/opencode/github` workflow запускает тот же `opencode github run` через mise с фиксированной версией **1.19.5**. Это сохраняет сценарии App, но исключает запрос `releases/latest`, на котором падала сторонняя обёртка. Установка версии идёт через закреплённый `mise-action` с токеном GitHub для загрузок. `USE_GITHUB_TOKEN: "false"` сохраняет обмен самой интеграции через OIDC. Для команд `gh` внутри скиллов защищённый шаг получает `GH_TOKEN` из штатного токена Actions с `issues: write` и `contents: read`: чтение обсуждений, публикация спецификаций/тикетов и меток. Токен не выводится в лог; искать альтернативную авторизацию агенту не требуется.

Основная и вспомогательная модели явно заданы как `opencode/big-pickle`, генерация заголовка отключена; платная вспомогательная модель автоматически не выбирается. **Решение по `share`: публикацию сессий не используем.** В [OpenCode 1.19.5](https://github.com/anomalyco/opencode/blob/810c0eba1a7348036f8bdf61e6632d0c36c6876c/github/action.yml) параметр action `share` объявлен устаревшим и игнорируется, поскольку sharing сессий прекращён; переменная `SHARE` не задаётся. Результат команды публикуется комментарием в GitHub, отдельная публичная ссылка на сессию не создаётся.

На свежем runner checkout доставляет закоммиченные скиллы первого проекта из `.agents/skills/`, `skills-lock.json`, `AGENTS.md` и настройки GitHub Issues из `docs/agents/`; локальные пользовательские скиллы для работы CI не требуются. Workflow должен находиться в `main`: оттуда берётся версия для комментариев к issue. Комментарий к строке PR позволяет проверить версию workflow из PR до отдельного слияния.

Общий тайм-аут командного job — 40 минут; установка CLI — не более 1 минуты, шаг агента — 32 минуты. Сам процесс ограничен 1800 секундами с принудительным завершением через 10 секунд. После авторизованного запуска файлы интерфейса, `docs/design/`, `package.json` и скрипт снимков `capture-search-mockup.mjs` сохраняются на 14 дней в артефакте `opencode-work-<issue>-<run>-<attempt>`, в том числе при ошибке шага агента. Это позволяет забрать результат незавершённого макета из Actions; артефакт сам по себе не означает согласования или готовности к реализации. Concurrency объединяет запуски одной issue или PR, `cancel-in-progress: false` сохраняет текущую работу. GitHub может показать дополнительный пропущенный запуск на комментарий бота; повторного обращения к модели при этом нет. Новые настройки применяются к новым запускам, старый запуск нужно отменить отдельно.

### Путь нового обращения

Создайте issue словами пользователя, без технического решения. Автотриаж оставит
разбор и вопросы; для продолжения после ответа используйте `/oc разбери обращение
по скиллу triage, код пока не меняй`. Затем запросите `to-spec` по исходному issue
и всей переписке. Спецификация публикуется отдельным issue с `workflow:spec`.
После одобрения спецификации и разбиения `to-tickets` публикует `workflow:ticket`
с критериями и нативными зависимостями. Исходное обращение и артефакты связаны ссылками.
Человек подтверждает версию спецификации и список тикетов комментарием в исходном
issue. Ссылка на него передаётся в PR будущего `implement-spec`; существенное
изменение объёма требует нового согласования. Подробности — в
[правилах трекера](docs/agents/issue-tracker.md#incoming-request-handoff).

### Автоматический triage и ИИ-ревью PR

Это отдельные сценарии, которые не заменяют проверку команды `/oc`.

Workflow [opencode-triage.yml](.github/workflows/opencode-triage.yml) запускается на `issues: types: [opened]` только для авторов типа `User` с association `OWNER`, `MEMBER` или `COLLABORATOR`. Prompt запускает проектный `triage`: агент читает обсуждение, проверяет существующий код и оставляет конкретные вопросы при нехватке условий. Артефакты с `workflow:spec`, `workflow:ticket` или `ready-for-agent` пропускаются; скиллы ставят метку при создании issue. Запуски одного issue сериализованы через concurrency. Он использует тот же закреплённый CLI, OpenCode App, Actions secret и модель, что командный workflow. Общий тайм-аут job — 5 минут, установка — 1 минута, шаг агента — 4 минуты, процесс — 180 секунд с принудительным завершением через 10 секунд.

Workflow [opencode-pr-review.yml](.github/workflows/opencode-pr-review.yml) запускает отдельное read-only авторевью на `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`). Допускаются открытые недрафтовые PR из этого репозитория от владельца или `opencode-agent[bot]`. Критерии и формат отчёта передаются через [REVIEW.md](REVIEW.md). Устаревший запуск одного PR отменяется.

До установки инструментов и передачи ключа модели код резервирует попытку: **не больше трёх запусков авторевью на PR**, включая разные SHA и rerun. Отмена и ошибка после резервации расходуют попытку. Служебные записи `github-actions[bot]` в PR — устойчивый счётчик; ручные маркеры пользователей игнорируются. Запуски одного PR сериализованы. При исчерпании остаются причина, SHA и ссылка на run в комментарии, логе, summary и артефакте; модель не запускается. Этот отказ не означает, что продуктовые тесты упали. Не удаляйте записи счётчика для его обнуления.

Перед вызовом модели GitHub API собирает diff, правила и прямо связанные источники в снимок с проверенным SHA. Сетевые инструменты модели не выполняются: для совместимости с бесплатным провайдером `bash`/`read` видимы, но требуют подтверждения, которое закреплённый неинтерактивный CLI сразу отклоняет (`--no-auto --no-yolo --no-dangerously-skip-permissions`). Ошибка квоты/авторизации немедленно останавливает процесс без автоматического повтора. вступление или незавершённый ответ не принимаются за отчёт. Снимок и поток событий сохраняются вместе с результатом. Ревьюер использует бесплатную `opencode/mimo-v2.6-flash-free`, не меняет код и сверяется со связанными задачами и согласованием. Лимиты: две итерации на анализ заранее собранного контекста, процесс 420 секунд, шаг 8 минут, job 12 минут. Отчёт публикуется общим комментарием, реальные замечания — также к допустимым строкам diff. Публикатор повторно проверяет head SHA; устаревшие результаты не выдаются за актуальные.

Ручной повтор на открытом PR (только владелец; используется тот же счётчик):

```bash
gh workflow run opencode-pr-review.yml --ref main -f pr_number=123
```

Авторевью использует бесплатную `opencode/mimo-v2.6-flash-free`. В ручном запуске параметр `model` также допускает `opencode/big-pickle`; остальные модели отклоняются до запуска CLI. Выбор модели не обнуляет лимит PR. Автоматического повтора или переключения на платную модель нет. При `reason: length` без итогового текста ревью считается незавершённым, а не успешным.

Workflow [browser-review.yml](.github/workflows/browser-review.yml) независимо запускает собранное приложение на точном PR head с локальными данными. Проверяются основной, негативный и соседний сценарии поиска из [спецификации #84](https://github.com/lukyanzhukov/ai-for-developers-project-387/issues/84). Checker берётся с base-ветки, поэтому новый тест реализатора его не подменяет; при первом добавлении checker его исходный SHA также записывается. Артефакт `browser-...` содержит JSON/Markdown-отчёт, полный SHA приложения и checker, шаги actual/expected, результат и снимки. Он хранится 14 дней. Падение браузера даёт failed check; изменение head требует новой проверки. Для новой функции расширяйте независимые сценарии по согласованной спецификации отдельным изменением checker.

Метка PR `browser:keyboard` включает профиль `keyboard-search` по [спецификации #91](https://github.com/lukyanzhukov/ai-for-developers-project-387/issues/91): Escape в поле, сохранение фокуса/режима/даты, пустое поле/повторное нажатие, Escape вне поля и сохранение соседних действий. Без метки работает профиль `search`. Изменение метки запускает проверку заново. Если base-checker ещё не поддерживает нужный профиль, check падает вместо публикации общего отчёта как проверки клавиатуры. Проверенный профиль указан в JSON/Markdown и комментарии PR.

```bash
gh workflow run browser-review.yml --ref main -f pr_number=123
```

Для проверки, что регрессионный тест обнаруживает дефект, есть ручной workflow [regression-evidence.yml](.github/workflows/regression-evidence.yml):

```bash
gh workflow run regression-evidence.yml --ref main \
  -f pr_number=123 -f test_file=tests/upcoming-search.test.ts
```

Он переносит один проверенный файл тестов из head во временный worktree base, требует успешной сборки и отказа именно assertion-проверки, затем успешного прогона на head. История и рабочая ветка не переписываются. Ошибка окружения, сборки или тайм-аут не считается доказательством регрессии. Артефакт `regression-...` содержит SHA, оба лога, JUnit и результат. Сценарий запускайте с тестом новой исправляемой регрессии: уже работающий на base тест закономерно не даст ожидаемого отказа.

[Шаблон PR](.github/pull_request_template.md) включает источники, проверки, обоснование их глубины, риск, откат и приёмку. Слияние выполняет человек после проверки результатов для текущего head.
В командах, triage и PR-ревью каталог `${{ runner.temp }}/_github_workflow/` с данными события разрешён через `external_directory`. Остальные внешние каталоги, циклические действия (`doom_loop`), вопросы человеку и переходы в интерактивный режим плана отклоняются без ожидания подтверждения. Чтение `.env` и `.env.*` запрещено; `.env.example` разрешён. У аудитов отдельный неинтерактивный CLI с немедленным отклонением запросов разрешений; шаги анализа ограничены 8 минутами, процесс — 420 секундами с остановкой группы процессов при сбое.

Автоматическое ревью не заменяет проверки CI и пользовательскую приёмку. Изменения workflow команд и triage начинают действовать после попадания в `main`.

### Выпуски

После push в `main` workflow `release-please.yml` готовит release-PR с версией и `CHANGELOG.md`. После его слияния создаёт тег и GitHub Release. Публикации в npm и деплоя в этом workflow нет.

В Settings → Actions → General включите **Allow GitHub Actions to create and approve pull requests**. Используется встроенный `GITHUB_TOKEN`.
Созданный им release-PR не запускает CI автоматически: перед слиянием выполните `mise run check` на его ветке.

## Docker и Render

[Публичный сервис](https://call-calendar-386-o6lw.onrender.com).

Если сервис не открывается из РФ, попробуйте VPN: доступность может зависеть от провайдера и маршрута. Причина сетевых таймаутов при проверке не установлена; необходимость VPN — предположение.

```bash
docker build -t call-calendar:production .
docker run --rm --name call-calendar -e PORT=8080 -p 8080:8080 call-calendar:production
```

Адрес: <http://localhost:8080>. Контейнер слушает `0.0.0.0`, порт задаётся через `PORT` (по умолчанию 3000). Проверка готовности — `/api/health`. Остановка: `docker stop call-calendar`.

Для Render используйте Dockerfile из корня, один экземпляр и проверку `/api/health`. У сервиса с публичным Git URL после push нужно отдельно запустить деплой; для автоматического деплоя подключите репозиторий через Git provider credentials. Проверяйте SHA коммита и статус `live`.

Адрес MCP задан в `.codex/config.toml`. Для подключения выполните `codex mcp login render`, завершите OAuth и перезапустите сессию агента. Секреты храните вне Git.

Проверка работающего сервиса:

```bash
DEPLOYMENT_URL=https://call-calendar-386-o6lw.onrender.com mise run deployment:check
```

Команда проверяет создание типа, запись гостя, отказ при конфликте и список владельца. Она добавляет синтетические данные; нужен свободный слот в ближайшие 14 дней.

## Плановые аудиты

Два независимых GitHub Actions workflow работают на `main`: `todo-audit.yml` ищет
подтверждённые TODO/FIXME по понедельникам в **02:17 UTC / 09:17 Asia/Novokuznetsk**;
`lockfile-audit.yml` проверяет `pnpm-lock.yaml` ежедневно в **01:37 UTC / 08:37
Asia/Novokuznetsk**. Запуски одного аудита сериализованы без отмены предыдущего;
разные аудиты друг друга не ждут. Расписание GitHub может запускаться с задержкой.

OpenCode **1.19.5** по умолчанию использует бесплатную `opencode/big-pickle` для
`model` и `small_model`, генерация заголовка отключена. При ручном запуске input
`model` позволяет выбрать `opencode/mimo-v2.6-flash-free`; другие ID скрипт
отклоняет до запуска агента. Выбранная модель фиксируется в `agent-status.json`.
Автоматических повторов с другой моделью нет. Бесплатная квота определяется
провайдером: её исчерпание означает ошибку анализа, а не успешный аудит.
Нужен repository secret
`OPENCODE_API_KEY`. Агент получает снимок как недоверенные данные. Изменения файлов
запрещены; shell/read требуют подтверждения, которое закреплённый неинтерактивный
CLI автоматически отклоняет. Флаги автоматического одобрения явно выключены.
Это сохраняет запрет доступа и выполнения, но не удаляет tools из запроса:
полное удаление tools вызывает у бесплатного провайдера ложную ошибку лимита
([описание проблемы](https://github.com/anomalyco/opencode/issues/51193)). У job анализа только
`contents:read`, `issues:read`, `actions:read`; `issues:write` есть только у
отдельного publisher с `GITHUB_TOKEN`. OpenCode App и дополнительные write-токены
не нужны. Все Actions закреплены полными SHA, OSV Scanner **2.7.1** — SHA256
проверенного Linux-бинарника. Ни один аудит не меняет зависимости или lockfile.

TODO/FIXME извлекаются из tracked source на SHA запуска с путём, строкой и
контекстом. Generated/vendor/build/node_modules, навыки и учебные тексты исключены;
агент отклоняет учебные, устаревшие и неподтверждённые пометки с объяснением.
OSV сохраняет исходный JSON, stderr, exit code и число пакетов (`--all-packages`).
Код `0` означает чистый результат, `1` — находки: агент сначала оформляет отчёт,
затем job аудита завершается ошибкой, а publisher обрабатывает подтверждённые
находки. `127` — ошибка сканера, `128` — нет распознанных пакетов; остальные коды,
таймауты, пустой или некорректный ответ агента тоже дают ошибку с диагностикой,
без выдуманной уязвимости. Отсутствие кандидатов создаёт пустой валидный отчёт.
OpenCode запускается с явным `--dir`, cwd и `PWD` каталога артефактов; снимок
передаётся через stdin. JSONL и INFO-логи сохраняются по мере поступления в
`agent.jsonl` и `agent.stderr`, статус — в `agent-status.json`. Значения переменных
окружения с `TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `CREDENTIAL`, `AUTH` в имени
и заголовки авторизации скрываются в диагностике.
Ошибка провайдера (например, исчерпанный лимит или неверный API key) либо JSONL
событие `error` немедленно завершает процесс агента вместе с его дочерними
процессами; общий таймаут остаётся 420 секунд. Причину конкретного сбоя следует
смотреть в этих артефактах; ошибка агента не переключает аудит на платную модель.

Publisher просматривает все страницы открытых и закрытых issues и комментариев,
включая ручные задачи. Ключ TODO — путь и текст без номера строки; повторные
сведения не публикуются, содержательные изменения контекста дают один комментарий.
Пробелы и пустые строки вокруг неизменной TODO-пометки не считаются новыми фактами.

OSV создаёт не более одной задачи с меткой `needs-triage` на экосистему, пакет и
версию. Все advisory этой версии объединены в компактную таблицу; полные scanner
reports и исходные описания остаются в artifacts. HTML в данных таблицы и заголовка
экранируется, чтобы текст advisory не мог стать служебным маркером. Scope зависимости (production/dev),
условия срабатывания и достижимость требуют проверки: совпадение в lockfile само
по себе не доказывает эксплуатацию в production. При хотя бы одном подтверждённом
кандидате publisher учитывает все исходные advisory пакета, включая отклонённые
агентом. Новые содержательные факты дают не более одного комментария на пакет.

Каноническая OSV-задача определяется маркером `audit-package` с экосистемой, пакетом
и версией; открытые задачи имеют приоритет, затем выбирается меньший номер.
При отсутствии такого маркера используется сопоставление прежних advisory-задач
и ручных задач. Если выбранная ручная OSV-задача совпала хотя бы с одним advisory,
но не содержит fingerprint, publisher сохраняет `skip` для всего пакета, включая
остальные advisory: без исходной базы фактов новые сведения нельзя доказать.
Состояния задач
не меняются: автоматических close и reopen нет.

Для каждого advisory сохраняются прежние `audit-identity` и `audit-fingerprint`:
экосистема, пакет, версия, группа пересекающихся aliases и fingerprint исходных
фактов. Перефразирование ответа агента или изменение подтверждённого подмножества
не порождает повторную публикацию. В fingerprint не входят время и URL запуска.
Решение `create`/`comment`/`skip`, причина (в том числе причина отклонения кандидата),
fingerprint и связанные URL сохраняются отдельно для каждого кандидата в
`decisions.json`. Ошибка API делает job публикации неуспешным.

Результаты доступны в summary и artifacts (30 дней): `todo-audit-input` /
`osv-audit-input` содержат `input.json`; `*-audit-report` — результат агента,
Markdown и сырую диагностику; `*-audit-publication` — решения publisher и его
диагностику. Artifacts загружаются также при ошибках. Отчёты не коммитятся.

После разрешённого слияния можно запустить каждый workflow вручную:

```bash
gh workflow run todo-audit.yml --ref main
gh workflow run lockfile-audit.yml --ref main
# Ручной выбор другой разрешённой бесплатной модели
gh workflow run todo-audit.yml --ref main -f model=opencode/mimo-v2.6-flash-free
gh workflow run lockfile-audit.yml --ref main -f model=opencode/mimo-v2.6-flash-free
```

Для повторной обработки сохранённого снимка укажите ID завершённого запуска
того же workflow в этом репозитории на `main` (пока его artifact не истёк):

```bash
gh workflow run todo-audit.yml --ref main -f source_run_id=123456789
gh workflow run lockfile-audit.yml --ref main -f source_run_id=123456790 -f model=opencode/mimo-v2.6-flash-free
```

Replay сохраняет в снимке `originRunId` исходного запуска отдельно от текущего
запуска обработки и проверяет SHA снимка по исходному запуску. Для источника
artifact и исходного запуска проверяются репозиторий, workflow, завершённость,
событие schedule/dispatch и ветка `main`; также проверяется схема снимка.
Поэтому цепочки replay работают и после продвижения `main`. Скачивается только
свой input artifact, данные анализируются заново с той же дедупликацией.
Publisher исполняет код из доверенного checkout `main`, не из artifact. Dispatch
из другой ветки пропускает оба job. Локальная проверка CLI и fake GitHub boundary:
`mise run audit:test` (также входит в `mise run check`).

Изолированная учебная проверка `ignoreUntil` запускается только вручную:

```bash
gh workflow run lockfile-audit.yml --ref main -f exercise_ignore_until=true
```

Учебная проверка выполняется до обращения к агенту, поэтому её отчёты сохраняются
также при недоступности бесплатной модели. Она создаёт временные lockfile с одной уязвимой и исправленной версией вне
рабочего проекта, проверяет future/expired исключение с конкретным advisory и
причиной, сохраняет raw reports/exit codes в artifact. Часы и исключения рабочего
проекта не меняются. Для локального запуска: `node scripts/osv-ignore-lab.mjs
--scanner /absolute/path/to/osv-scanner --output /tmp/osv-ignore-lab`.

Демонстрация после отдельного разрешения слияния: повторить снимок и проверить
отсутствие дубликатов, затем сравнить `gh run cancel RUN_ID` (отмена одного
запуска) с `gh workflow disable todo-audit.yml` и `gh workflow enable
 todo-audit.yml` (выключение/включение будущих запусков). Эти команды здесь только
инструкция; фактические запуски, публикация issues и пользовательская приёмка
сообщаются отдельно.
